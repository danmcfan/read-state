Why Discord moved Read States from Go to Rust

A short explainer of Discord's 2020 rewrite, plus the same cache running live in your browser, built from Go and from Rust.

Source on GitHubDiscord's original post

#What is the Read States service?

Every time you open a channel, Discord needs to know which messages you have already read. The Read States service tracks that: one small record per user, per channel, holding things like the last message read and the mention count.

It sits on the hot path. It is hit on every connection, every message sent, and every message read, so it has to be fast all the time, not just on average.

To keep it fast, each instance keeps recently used read states in memory in an LRU cache holding millions of entries, and writes changes back to the database.

An LRU (least recently used) cache has a fixed number of slots. A write to an entry that is already cached moves it to the front. A new entry goes in front too, and when the cache is full the entry at the back, the one untouched for longest, is evicted. Step through it:

#The problem: garbage collection spikes

The Go version was mostly fast, but every couple of minutes it showed large latency and CPU spikes.

The cause was Go's garbage collector. Go forces a collection at least every two minutes, and each collection has to scan the whole heap to find what is still alive. With an LRU cache holding millions of long-lived entries, that scan was large even though very little garbage was being created.

Tuning helped only so much. Discord split the cache into smaller ones and tried smaller sizes. Shrinking the cache made each scan cheaper, but more requests missed the cache and went to the database, so tail latency got worse.

#The fix: rewrite it in Rust

Rust has no garbage collector. Memory is freed as soon as its owner goes out of scope, so an evicted cache entry is freed the moment it is evicted. There is no periodic pass over the whole heap.

Go version

  • Garbage collected
  • Spikes every ~2 minutes as the GC scans the cache
  • Bigger cache meant bigger GC pauses

Rust version

  • No GC; ownership frees memory on eviction
  • No periodic spikes
  • Cache could grow without a GC cost

Discord reported that even with only basic optimization, the Rust port outperformed the hand-tuned Go service, and after some profiling it beat Go on latency, CPU, and memory. Without a GC cost, they could also raise the cache capacity to 8 million read states, which cut database reads further. Along the way they swapped the cache's HashMap for a BTreeMap to save memory.

#Watch it live

The same cache, compiled to WebAssembly, runs right here in your browser: the Go and Rust builds, each in its own worker. Every point is one batch of reads and writes to a full cache, run back to back; dashed lines mark Go garbage collections.

One thing differs from the problem above: here the spikes follow heap growth, not a two-minute timer. Go's WASM runtime has no background monitor thread, so the forced GC never fires, and every collection is triggered by the heap growing. It is also single-threaded, so each collection pauses the whole program instead of running beside it on other cores.

Try this

  • Press Run Go and watch for its spikes: each one sits on a dashed line, a collection.
  • Press Run Rust beside it and see a flat line: Rust frees memory as it goes, with nothing to collect.
  • Press Force GC while Go runs and watch for a spike on a new dashed line.
  • Raise the Cache size and see Go's spikes grow taller: each collection has more entries to scan.
  • Batch size sets the work per point: raise it and see both lines climb together.
  • Push the Read ratio to 100% and watch Go's collections stop: with no writes, nothing in the cache changes and nothing new needs collecting.
  • Switch the Go layout to Pointer-free and see Go's spikes all but vanish; the next section explains why.

#Could Go keep up without pointers?

Go's collector only has to trace memory that holds pointers. Pointers is Discord's original layout: a map of pointers into container/list, where every entry is a heap object the collector must trace. Go can also hold the cache as one slice of fixed-size slots linked by index, with a map from key to slot index, the same design as the Rust cache. Neither holds a pointer, so the collector marks them as having nothing inside to scan.

Try it: in the chart above, run Go, switch the Go layout to Pointer-free, and press Force GC. Go refills its cache in the new layout, and its spikes all but vanish.

The comparison flatters Go a little: Discord's real read states held more than two integers, and anything with a string, timer or pointer in it would put the collector back to work.
